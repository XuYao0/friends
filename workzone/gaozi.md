# 1. 开场与题目介绍

## 讲述内容

各位老师好，我的中期汇报题目是**《基于剧本叙事的长期对话情感识别基准与记忆增强 Agent 研究》**。

这个题目主要关注一个问题：在长篇对话里，一个人当前说话时的真实情绪，往往不能只看这一句话，而要结合之前发生过的事件、人物关系、性格特点和长期状态来判断。

所以我的研究一方面是构建一个长期对话情感识别基准，另一方面是设计一个带有长期记忆机制的情感识别 Agent，让它像读剧本一样按顺序阅读，并在每个评测点判断说话人的真实情绪。

## 备注信息

这里要突出两个关键词：

第一是**长期对话情感识别（Long-Term Emotion Recognition in Conversation）**。它不同于传统 ERC（Emotion Recognition in Conversation），不是只判断当前句或附近几轮对话的情绪，而是考察长期叙事上下文中的真实情绪。

第二是**记忆增强 Agent（Memory-Augmented Agent）**。本项目不是简单把很长的上下文塞进 LLM，而是希望让系统在线构建人物状态、事件记忆和关系记忆，再在预测时按需检索。

可以强调：
这个课题不是单纯做一个分类器，而是构建一个可运行、可记录、可消融的长期情绪理解实验框架。

# 2. 研究背景：为什么需要长期情绪理解？

## 讲述内容

传统对话情感识别通常根据当前句、前后几轮对话，或者当前场景来判断情绪。这种方法在短对话里是有效的，但在长期对话中会遇到问题。

因为很多情绪不是由当前一句话直接决定的，而是来自更早的关系变化、冲突、承诺、误会，或者人物稳定的性格特点。

比如一句“Good morning.”，表面上是普通问候，但如果结合人物关系和语境，它可能其实是讽刺、厌烦，甚至轻蔑。所以我关注的不是台词表面情绪，而是说话人在当前时刻的真实情绪。

## 备注信息

这里可以解释“真实情绪”和“表面情绪”的区别：

* **表面情绪（Surface Emotion）**：当前句子字面上表现出来的情绪，比如礼貌、平静、玩笑。
* **真实情绪（True Emotion）**：结合上下文后，角色实际可能处于的心理状态，比如压抑、嫉妒、内疚、尴尬、恐惧。
* **表面与真实情绪不一致（Surface-True Emotion Mismatch）** 是本项目的重要长程依赖类型之一。

可以举的例子：

“Good morning.”
如果没有上下文，可能标为 neutral。
但如果前面人物之间有不愉快，或者这个问候是对某个不受欢迎的人说的，就可能是 contempt 或 anger。

这说明长期情绪理解需要的不只是语言理解，还包括**关系历史（Relationship History）**、**事件记忆（Event Memory）** 和 **角色特质（Character Trait）**。

# 3. 文献调研：领域趋势

## 讲述内容

从文献上看，最近情感计算和长期记忆两个方向都在发生变化。

情感计算方面，研究正在从简单的情绪分类，逐渐转向更细粒度的情绪描述、长上下文情绪理解，以及带有心理学理论的情感推理。比如 ETC 直接让模型生成情感描述，LongEmotion 关注长上下文情感智能，Appraisal Theory 相关工作则把情绪看成一种认知评价过程。

记忆机制方面，MemoryBank、MemGPT、A-Mem 和 Mem0 都说明一个趋势：LLM 不能只依赖固定上下文窗口，而需要外部长期记忆。不同工作分别从遗忘曲线、类操作系统记忆管理、卡片盒笔记法、生产级记忆系统等角度来组织长期记忆。

我的课题正好处在这两个方向的交叉点上：一方面关注长期情绪识别，另一方面使用显式记忆机制来支持情绪推理。

## 备注信息

这一页可以按两个方向展开。

**一、情感计算方向（Affective Computing）**

可以提到以下趋势：

1. **从分类到描述**
   ETC（Emotion Transcription in Conversation）提出让模型生成自然语言情绪描述，而不是只输出 anger、sadness 这类标签。
   启发：真实情绪往往是混合、细腻、带原因的。

2. **从短上下文到长上下文**
   LongEmotion 关注长上下文下的情感智能，包括情绪识别、情绪问答、情绪摘要、共情对话等。
   启发：情感能力不只是单句分类，而是长期信息整合能力。

3. **从表层语义到心理机制**
   Appraisal Theory（认知评价理论）相关工作把情绪理解为“事件—目标—评价—情绪”的推理过程。
   启发：本项目可以不只标情绪标签，还记录触发原因、历史证据和推断过程。

4. **从结果监督到过程监督**
   AFlow、RLVER、EmotionThinker 等工作说明，情感生成和情感识别都开始关注中间推理过程，而不是只看最终答案。
   启发：本项目 analysis 字段中区分 observable facts、memory evidence、inferences 和 uncertainties 是有意义的。

**二、长期记忆方向（Long-Term Memory）**

可以提到：

1. **MemoryBank**
   重点是 AI 陪伴场景，引入用户画像和遗忘曲线（Ebbinghaus Forgetting Curve）。
   启发：长期交互中，用户状态和长期偏好很重要，但记忆组织相对粗。

2. **MemGPT**
   把 LLM 类比为 CPU，把上下文窗口类比为 RAM，把外部记忆类比为硬盘，用类操作系统方式管理上下文。
   启发：LLM 不应被动接收全部历史，而应主动读写记忆。

3. **A-Mem**
   借鉴 Zettelkasten（卡片盒笔记法），让记忆之间自动建立链接，并随新经验更新旧记忆解释。
   启发：长期情感记忆也应该会演化。早期一句话的意义，可能要在后续事件中重新理解。

4. **Mem0**
   强调生产可用的长期记忆系统，通过 LLM 判断 ADD、UPDATE、DELETE、NOOP，也有图增强版本 Mem0g。
   启发：记忆系统需要关注准确性、更新策略和效率，而不是无限存储。

最后可以总结：
我的方法不是照搬某一篇，而是把这些思想迁移到**长期对话情感识别**这个更具体的任务中。

# 4. 研究问题与目标

## 讲述内容

我的研究目标可以概括为两点。

第一，构建一个基于 Friends 剧本的长期对话情感识别基准。这个基准重点筛选那些需要长期上下文才能判断情绪的台词。

第二，设计一个记忆增强 Agent。它按剧情顺序在线阅读剧本，在预测第 t 句台词时，只能使用第 t 句以及之前的信息，不能提前看到未来剧情。

最终希望模拟的是：一个 AI 从头读一部长篇剧本，在不断积累记忆的过程中，判断当前台词体现的真实情绪。

## 备注信息

这里的核心是**在线约束（Online Constraint）**。

老师可能会问：“为什么不直接把整集或整季塞给模型？”

可以回答：

1. 直接输入完整剧本会违反真实长期交互场景。真实 Agent 在当前时刻只能知道过去，不能知道未来。
2. 如果使用完整剧本提前生成全局摘要，会产生信息泄漏。
3. 本项目希望检验的是“在线构建的长期记忆是否有助于情绪识别”，而不是检验模型读完整剧情后的总结能力。
4. 这种设定更接近实际 AI 伴侣、长期助手和心理支持系统。

可以补充三个约束：

* **在线约束（Online Constraint）**：只能用当前及之前信息。
* **真实情绪约束（True Emotion Constraint）**：判断说话人的真实情绪，而不是字面情绪。
* **可解释约束（Explainability Constraint）**：不仅输出标签，还要说明事实、证据、推断和不确定性。

这些内容与综合文档中的任务定义和目标一致。

# 5. 数据集构建

## 讲述内容

数据方面，我选择 Friends 剧本作为主要来源。原因是它有稳定的主角群、连续的人物关系、跨 episode 的情感冲突，也有大量场景说明和动作描写，比较适合构造长期叙事情绪理解任务。

目前已经从原始剧本文本中清洗出六万多条台词和八千多条场景说明。然后我用大语言模型从中筛选需要长期上下文的候选台词，最后得到八千多条候选样本。

目前已经先标注了第三季的 300 句台词，用来验证 Agent 设计是否可行。

## 备注信息

这里要注意防守两个问题。

**问题一：为什么用电视剧剧本，而不是现实对话？**

可以回答：

真实长期对话数据很难获得，存在隐私、授权、标注成本和上下文缺失问题。剧本虽然不是现实对话，但它有几个优势：

* 人物关系稳定；
* 事件发展连续；
* 冲突和情绪线索丰富；
* 场景说明可以作为可观察环境信息；
* 历史证据容易回溯；
* 隐私风险低。

所以本项目不声称 Friends 等价于真实对话，而是把它定位为**基于剧本叙事的长期情绪理解基准（Narrative-Based Long-Term Emotion Understanding Benchmark）**。

**问题二：怎么筛选长期依赖样本？**

目前使用 LLM-assisted 筛选。给模型 50 句台词和对应 episode 简介，让它判断哪些台词需要长期信息才能理解情绪。

筛选时定义四种长程依赖类型：

1. **relationship_history（关系历史）**
   情绪依赖过去恋情、冲突、分手、承诺、嫉妒等。

2. **character_trait_or_habit（角色特质或习惯）**
   情绪依赖稳定性格，如讽刺、防御、控制欲、不安全感。

3. **past_event_reference（过去事件指涉）**
   台词隐约指向早前事件，比如“又来了”“那件事”。

4. **surface_true_emotion_mismatch（表面与真实情感不符）**
   表面像玩笑或礼貌，真实可能是尴尬、内疚、恐惧等。

同时给模型明确的反例规则：
不要把普通玩笑和当前场景就能判断的情绪误选为长程依赖样本。

**问题三：当前标注是不是 gold label？**

目前更准确地说是 **silver label（银标）**。因为主要由高强度 reasoning 模型辅助标注，后续还需要人工抽查、多模型一致性或 judge 机制来提升可靠性。

# 6. 情绪标签体系

## 讲述内容

标签体系方面，我没有直接照搬某一个基础情绪理论，而是结合 Ekman、Izard 和 Plutchik 的理论，再根据 Friends 长期对话的实际需求进行调整。

当前标签包括 anger、disgust、fear、happiness、surprise、sadness，也保留了 contentment、relief、interest、contempt、shame、guilt、embarrassment 和 neutral。

这样做是因为长期对话中很多情绪不是简单的喜怒哀乐，比如尴尬、内疚、轻蔑、如释重负，这些情绪在人物关系和情节发展中非常常见，也有独立的心理评价结构。

## 备注信息

老师可能会问：“为什么不直接用 Ekman 六大情绪？”

可以回答：

Ekman 六大情绪适合基础情绪识别，但对长期对话不够细。长期叙事中大量情绪属于社会性情绪或自我意识情绪，例如：

* **guilt（内疚）**：认为自己伤害了别人或违反责任；
* **shame（羞耻）**：自我形象或身份受到否定；
* **embarrassment（尴尬）**：轻度社交失误或私人信息暴露；
* **contempt（轻蔑）**：认为对象低劣、不值得尊重；
* **relief（如释重负）**：威胁解除后的放松；
* **contentment（满足）**：需求满足后的平静正向状态；
* **interest（兴趣）**：注意力被吸引并想继续了解。

这些标签不是简单的强弱变化，而是有不同的**认知评价结构（Appraisal Structure）**。

比如 shame 和 guilt 的区别：

* guilt 指向“我做错了事”；
* shame 指向“我这个人有问题”；
* embarrassment 通常更轻，指向社交暴露或场面不合适。

强度标签包括：

* low；
* medium；
* high；
* neutral 对应 none。

标注规则是 emotions 和 intensities 一一对应，neutral 不能和其他情绪并列。

# 7. 任务定义与输出格式

## 讲述内容

任务形式上，输入是一串按时间顺序排列的剧本内容，包括台词、说话人、场景说明和动作描写。

对于目标台词，系统需要输出三类内容：情绪标签、情绪强度，以及一段结构化分析。

这个分析不仅要说明为什么选这个情绪，还要区分当前可观察事实、历史记忆证据、模型推断和不确定性。这样可以帮助我们判断模型是不是真的利用了长期记忆。

## 备注信息

可以展开解释 output schema：

```json
{
  "emotions": ["contempt"],
  "intensities": ["medium"],
  "analysis": {
    "observable_facts": [],
    "memory_evidence": [],
    "inferences": [],
    "uncertainties": [],
    "final_reason": ""
  }
}
```

各字段意义：

* **observable_facts（可观察事实）**：当前台词、动作、场景中直接可见的信息。
* **memory_evidence（记忆证据）**：从历史事件或人物状态中检索到的证据。
* **inferences（推断）**：基于事实和记忆做出的心理解释。
* **uncertainties（不确定性）**：证据不足或多种解释并存的地方。
* **final_reason（最终理由）**：简洁总结为什么判断为该情绪。

这个设计有两个作用：

1. 让模型的情绪判断更可解释；
2. 方便后续错误分析，比如看错因是检索失败、记忆更新错误，还是情绪标签混淆。

# 8. AC Agent 总体架构

## 讲述内容

模型方面，我设计了一个 AC Agent 原型。它的核心思想是：外层用确定性的 workflow 保证剧情顺序，内层用 LLM tool-calling 来完成事件检索、事件读取、记忆更新和情绪推理。

也就是说，系统不是把全部历史一次性输入模型，而是让 Agent 一边读剧本，一边更新记忆。到达评测台词时，它可以先查看当前人物状态和当前事件，再通过工具检索相关历史事件，最后输出情绪判断。

## 备注信息

架构可以拆成两层。

**第一层：确定性外层 workflow**

作用是保证在线顺序。
数据源按原始顺序读取 description 和 utterance。

* 普通台词累积到一定 batch 后，进入 memory update；
* 如果遇到 long_context_selected = true 的台词，进入 label；
* 如果评测点在 batch 中间，只能用评测点之前的信息。

这样可以避免未来信息泄漏。

**第二层：LLM tool-calling 内层**

Agent 可以调用三个核心工具：

1. `search_events`
   检索可能相关的历史事件索引。

2. `read_event`
   读取某个事件的详细描述。

3. `update_memory`
   将人物状态、关系状态、事件和当前事件变化写入记忆。

可以强调：
tool-calling 的好处不是为了炫技，而是为了让记忆使用过程可记录、可复现、可消融。后续可以分析每次预测时模型到底检索了什么、读了什么、是否引用了历史证据。

# 9. 记忆结构设计

## 讲述内容

AC Agent 的记忆主要分成四类：人物状态、事件索引、详细事件记忆和当前事件。

人物状态用来保存角色的长期和短期状态，比如性格特点、近期压力、关系状态。事件索引用来快速检索历史事件。详细事件记忆保存更完整的事件描述。当前事件则记录当前 scene 内已经发生的内容。

这样设计的目的，是把“长期稳定背景”和“具体历史事件”分开，避免把全部历史都塞进 prompt。

## 备注信息

四类记忆可以详细解释：

**一、人物状态（Character State）**

包含：

* recent_events：近期影响人物的事件；
* short_term_traits：短期状态，如当前目标、压力、需求；
* long_term_traits：长期特质，如人格倾向、稳定脆弱点；
* relationships：人物视角下的人际关系状态。

每条记忆是 MemoryItem，区分：

* fact；
* inference；
* uncertain。

这可以避免模型把不确定推断当成事实。

**二、事件索引（Event Index）**

类似一个可检索目录，包含：

* event_id；
* scene_id；
* characters；
* keywords；
* short_summary；
* importance；
* knowledge_scope；
* detail_id。

首版检索基于关键词、人物、地点、摘要和重要性。

**三、详细事件记忆（Event Detail）**

保存完整事件描述，但默认不进入 prompt。
Agent 必须先 search，再 read。
每个评测点默认最多读取 3 个详细事件，防止退化成全文输入。

**四、当前事件（Current Event State）**

保存当前 scene 内已经发生的近距离上下文。
它比长期事件优先级更高，但也必须只包含当前 utterance 之前的信息。

可以强调：
这个记忆结构和 Mem0、A-Mem 的启发有关，但更加面向情感识别任务。它不是通用事实记忆，而是为人物状态、关系变化和事件触发情绪服务。

# 10. 当前实现进展

## 讲述内容

目前系统已经实现了首版原型。

包括主 workflow、记忆更新分支、情绪标注分支、工具调用模块、本地 JSON 记忆存储、JSONL 预测结果保存，以及 trace 日志记录。

系统能够按剧本顺序读取 Friends 数据，遇到普通 batch 就更新记忆，遇到评测点就调用 Agent 进行情绪预测。目前核心程序路径已有基础测试覆盖，当前测试状态是 55 passed。

## 备注信息

可以展开说已经实现的模块：

* `WorkflowRunner`
* `MemoryUpdateLoop`
* `LabelLoop`
* `ToolExecutor`
* `ToolRegistry`
* `AgentTool`
* `FriendsTranscriptChunkSource`
* `MemoryState`
* `JsonMemoryStore`
* `JsonlPredictionStore`
* `JsonlTraceWriter`
* 三个核心工具：`search_events`、`read_event`、`update_memory`

输出目录包括：

* memory；
* predictions；
* traces。

trace 很重要，因为后续不仅看最终准确率，还可以分析：

1. 预测时用了哪个 memory version；
2. 是否调用了 search_events；
3. 检索结果是什么；
4. 是否读取了详细事件；
5. 最终回答是否引用了记忆；
6. JSON 解析是否成功。

这为后续消融实验和错误分析提供基础。

# 11. 初步实验结果

## 讲述内容

目前实验还比较初步，主要是为了验证方向是否可行。

我在已经标注的 300 句台词上比较了三种设置：只给单句台词、给目标句和前 14 句上下文、以及使用当前 AC Agent。

结果上，单句台词的 emotion 完全一致率是 18.33%，15 句上下文是 26.67%，Agent 是 27.67%。如果看 emotion 有任一重叠，单句是 61.67%，15 句上下文是 70.67%，Agent 是 72.00%。

这说明目前 Agent 还没有形成明显优势，但相比单句和短上下文已经有一定提升。更重要的是，它证明了这套在线记忆框架可以跑通，后续可以进一步优化记忆质量和检索策略。

## 备注信息

实验结果要讲得稳，不要夸大。

可以说：

目前结果只能说明“初步可行”，不能说明方法已经显著优于短上下文。

具体数据：

**单句台词：**

* emotion 集合完全一致：55 / 300，18.33%
* emotion 任一重叠：185 / 300，61.67%
* emotion+intensity 成对完全一致：32 / 300，10.67%

**15句上下文：**

* 多标签集合完全一致：80 / 300，26.67%
* 任一 emotion 重叠：212 / 300，70.67%
* 完全无重叠：88 / 300，29.33%

**Agent：**

* 预测覆盖：298 / 300，99.33%
* emotion 集合完全一致：83，按 300 算 27.67%
* emotion 任一重叠：216，按 300 算 72.00%
* emotion+intensity 对完全一致：42，按 300 算 14.00%
* 完全无重叠：82，按 300 算 27.33%

答辩时如果老师问“为什么提升不大”，可以回答：

1. 当前标注样本只有 300 条，统计不稳定；
2. 事件检索还是关键词为主，语义检索不足；
3. 记忆更新没有压缩、去重、冲突消解；
4. 当前 Agent 还可能没有充分学会什么时候该检索历史；
5. 15 句上下文本身已经包含了很多局部信息，所以差距不会特别大；
6. 更关键的实验应该按长程依赖类型分层，看 relationship_history、past_event_reference 等子集上的表现。

可以补充：
中期阶段的重点不是最终 SOTA，而是验证任务定义、数据流程和 Agent 框架能否闭环。

# 12. 预期贡献

## 讲述内容

目前我认为这个项目的贡献主要有五点。

第一，提出一个基于剧本叙事的长期对话情感识别任务设定。

第二，构建 Friends 长期情绪理解基准，保留台词、说话人、场景说明和剧情顺序。

第三，设计适合长期对话的情绪标签体系，保留一些社会性和自我意识情绪。

第四，提出 AC Agent 原型架构，用在线增量记忆和 tool-calling 支持情绪识别。

第五，系统记录完整 trace，方便后续做消融实验和错误分析。

## 备注信息

可以把贡献和已有工作区分开：

**相对传统 ERC：**

传统 ERC 多是短上下文、固定窗口、直接分类。
本项目强调：

* 长期依赖；
* 在线约束；
* 真实情绪；
* 可解释分析；
* 记忆证据。

**相对 LongEmotion：**

LongEmotion 更像综合情感智能 benchmark，任务覆盖范围广。
本项目更聚焦在“剧本叙事中的长期真实情绪识别”，任务更窄，但 memory 和 online reading 约束更明确。

**相对 MemoryBank / MemGPT / A-Mem / Mem0：**

这些主要是通用长期记忆系统。
本项目的不同点在于：记忆结构是为情绪识别设计的，尤其关注人物状态、关系变化、事件触发和真实情绪解释。

可以强调一句：
本项目不是单独提出一个新记忆系统，也不是单独提出一个情感分类数据集，而是把长期记忆机制引入长期情绪识别任务中，形成一个可实验的闭环。

# 13. 当前问题与风险

## 讲述内容

目前项目也有一些问题需要后续解决。

第一，当前标签主要是 LLM-assisted silver label，质量还需要人工抽查和一致性验证。

第二，Friends 是知名剧集，模型可能带有参数化知识，所以后续需要做匿名化实验，控制知识泄漏。

第三，当前记忆更新还比较粗，缺少自动去重、冲突消解和压缩。

第四，事件检索目前主要依赖关键词，对于隐含关系和语义呼应还不够。

第五，评测样本还需要更严格地验证，确保它们确实需要长期上下文。

## 备注信息

这页要表现出你对风险有清醒认识。

**silver label 风险**

LLM 标注可能有：

* 过度推断；
* 受预训练剧情知识影响；
* 对复杂混合情绪不稳定；
* 和人类标注偏好不一致。

解决方案：

* 人工抽查；
* 多模型一致性；
* LLM-as-a-Judge；
* 重点样本人工复核；
* 计算标注一致性。

**参数化知识泄漏（Parametric Knowledge Leakage）**

因为 Friends 很有名，模型可能已经知道角色关系。
解决方案：

* 替换人物姓名；
* 匿名化 episode 信息；
* 对比原名版和匿名版；
* 更严格时只提供在线可见信息。

**记忆噪声问题**

长期运行后，人物状态可能：

* 重复；
* 过时；
* 冲突；
* 膨胀；
* 被不确定推断污染。

解决方案：

* memory compression；
* 状态版本控制；
* fact / inference / uncertain 区分；
* 冲突检测；
* 过期记忆降权。

**检索问题**

当前关键词检索难以处理：

* 语义相似；
* 隐喻；
* 人物关系暗示；
* 跨场景呼应；
* “那件事”这类间接指代。

解决方案：

* 在线 embedding；
* hybrid retrieval；
* 按人物关系和事件类型建立索引；
* 记录 retrieval recall。

# 15. 总结

总结一下，目前这个项目已经明确了研究问题、任务边界、标签体系、数据构建流程和 Agent 架构，也实现了首版 AC Agent 原型。

当前阶段的重点不是已经取得很高的性能，而是建立了一个可以系统研究长期情绪理解的实验框架。这个框架可以帮助我们回答：长期上下文是否真的有用，显式记忆是否优于简单长窗口，人物状态和事件记忆如何帮助情绪识别，以及模型的分析是否真正引用了历史证据。

## 备注信息

最后一句可以稍微强调研究价值：

这个项目的长期意义在于：
如果 AI 要做长期陪伴、心理支持或个性化助手，它不能只理解当前一句话，而要记住用户过去发生了什么、关系如何变化、哪些事件对用户有持续影响。

因此，长期情绪识别既是一个情感计算问题，也是一个记忆与推理问题。
本项目希望提供一个可控的数据环境和原型系统，为后续研究“记忆如何支持情绪理解”打基础。
